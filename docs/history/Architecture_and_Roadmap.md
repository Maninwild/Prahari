# Prahari — Project Audit, Architecture and Development Roadmap

Prepared 13 September 2026. Scope: the two supplied ZIP archives. This is the implementation baseline for a unified hackathon product; implementation has not started.

**Product decision**

Prahari will give small web application teams one place to inspect suspicious links and incoming requests, understand evidence, and apply an auditable protection policy. One analysis service, one finding format, one decision engine and one history store will power both interactive scans and backend integration. Specialized models remain appropriate because phishing destinations and attack payloads are different prediction tasks.

The initial protection demonstration will integrate with one developer-owned demo application. Pasting a URL into the scanner produces an advisory decision; actual enforcement occurs only in an integrated request or link-submission workflow. Prahari will not claim to protect arbitrary browsing or establish that an application is exploitable.

**Inspection coverage and verification**

Reviewed every authored Python module, both application interfaces including embedded CSS/JavaScript, the training notebook, requirements, README files, demo guide, Windows launcher, editor configuration, and extracted explanation-document text. Profiled the complete phishing CSV; loaded and inspected both model/scaler artifacts; visually inspected both saved plots. Inventoried generated bytecode caches but did not treat them as canonical source. Original archives remain unchanged.

Executed all 12 SentinelAI functional tests successfully, including its Node.js control harness. Loaded the phishing forest and scaler without compatibility warnings in this environment. Ran targeted prediction and normalization probes. These checks are not a production benchmark. Neither full UI was launched in a browser, the full training pipeline was not rerun, and saved historical metrics were not independently reproduced.

**Weaknesses and evidence**

1. **Phishing dataset shortcut — critical.** All 134,850 raw legitimate rows have a www-prefixed hostname and no path. The remaining 100,945 rows carry the phishing label. After URL deduplication the expected usable row count is 235,370, consistent with the README. The saved forest's global importance is 41.40% HTTPS and 28.57% slash count. Together with the probes below, this strongly suggests reliance on dataset construction artifacts. Global importance alone is not a local explanation or proof of causation.

| Supplied model probe | P(phishing), rounded |
|---|---:|
| https://www.github.com | 1.89% |
| https://github.com | 99.01% |
| https://github.com/openai | 100.00% |
| https://www.google.com/search?q=weather | 100.00% |
| https://www.microsoft.com/en-us/ | 93.11% |

These are model outputs on supplied strings, not live reputation checks. They expose unacceptable behavior for a general-purpose link screener. Saved accuracy is 99.5879%, precision 99.9348%, recall 99.0997%, F1 99.5155%, on the old random split. The plot records TN=26,957, FP=13, FN=181, TP=19,923. Do not market this as Prahari performance.

2. **Feature bugs.** Shorteners are checked as substrings anywhere in the URL; microsoft.com matches t.co, and a query mentioning bit.ly triggers the same feature. Match a parsed, normalized hostname against explicit shortener domains. Splitting the netloc at ':' breaks IPv6; the probe https://[::1]/ produces a one-character domain and no IP flag. Use validated URL parsing, ipaddress, IDNA handling and registered-domain-aware features. Current dot-count subdomain estimation misreads suffixes such as co.uk. Input such as 'not a url' reaches phishing prediction instead of validation.

3. **Training workflow drift.** The notebook and augmentation script expect dataset/phishing_urls.csv, absent from the ZIP, while train_model.py reads the supplied PhiUSIIL CSV. The augmentation script overwrites its input and samples/replaces legitimate rows despite a docstring claiming it retains every original row. Its output is not consumed by the active training script. The generator assigns synthetic maliciousness by construction, including shorteners; it is not a substitute for independently labelled traffic. Forest selection is hardcoded rather than performed on a validation set. Requirements lack exact locks and artifacts lack dataset hashes, split manifests and environment provenance.

4. **Insufficient request-model evidence.** SentinelAI has no independent evaluation set or recorded accuracy benchmark. Its existing tests verify expected behavior, often on training-like examples. Multiclass ML chooses one class even when multiple attacks occur; rules already preserve multiple categories. Keep this distinction visible until multilabel training data justifies a different model.

5. **Normalization changes meaning.** Every original '+' is replaced with a space, including JSON: the probe {"value":"a+b"} becomes {"value":"a b"}. URL and HTML decoding apply to all text without content-type awareness. Parse first, retain raw input, and normalize specific components. Keep heuristic decoding as an additional view, not an assertion of what the backend executes. Flag unsupported content types or incomplete parsing instead of returning an unqualified Allow.

6. **Rules lack application context.** Searching for 'how to use UNION SELECT' triggers SQL Injection. Broad pattern matches should be Review signals until their context and false-positive rate justify enforcement. Command signatures cover a small list of utilities, and neither family rules nor two-pass decoding provide complete coverage. Define supported request formats and bounded work budgets.

7. **Product infrastructure is missing.** No durable database, tenant/project separation, access control, API keys, configurable policy, detector health, model version lineage or enforcement adapter. Raw credentials/cookies could appear in current histories and downloads. Detection must inspect authorized input in memory, then redact secrets before persistence, display or export; sensitive routes should suppress raw previews entirely.

8. **Current uncertainty is asymmetric.** PhiUSIIL calls every predicted legitimate URL LOW even near its class boundary. SentinelAI has a useful abstention rule (top probability 0.55 and margin 0.12), but those thresholds are unvalidated. Neither model is calibrated. A low score, a missing detector and an unparseable input must remain different states.

**Unified architecture**

Use a modular Python service and a single Angular/TypeScript frontend. Angular fits the developer's existing experience. FastAPI provides the typed API boundary and OpenAPI contract. Keep training offline and detector code independent of HTTP/UI code. Use SQLite with migrations for the single-instance local milestone; use PostgreSQL for a hosted multi-user deployment. Do not deploy ephemeral SQLite storage as durable history.

| Layer | Responsibility |
|---|---|
| Workspace UI | One scan composer accepting a URL, request or payload; one result panel with all findings; shared history, dashboard, integration settings |
| API boundary | Authentication, project scope, schemas, content/size limits, rate limits, request IDs |
| Parser | Produce typed URL/request components; preserve repeated query keys; handle JSON and form bodies; record ambiguous or unsupported input |
| Analysis orchestrator | Route applicable fields to detectors; enforce deadlines; retain complete/not_applicable/error/unsupported status |
| Phishing detector | Score explicit destination URLs using versioned features/model; no inference on arbitrary raw HTTP text |
| Request ML detector | Class distribution and learned feature evidence on supported request/payload views |
| Rule detector | Per-component, multi-family evidence on raw and appropriate decoded views |
| Fusion and policy | Category risks, unified risk, Allow/Review/Block decision, policy version and uncertainty reasons |
| Persistence | Redacted scans, findings, model and policy versions, review outcomes and enforcement events |
| Integration adapter | Call the same analysis contract before an application action, enforce configured disposition, acknowledge actual action |

Routing matters: the Host header of an incoming request identifies the protected application, not necessarily a phishing destination. For request scans, phishing applies to explicitly identified external link fields, such as a configured submitted URL or redirect destination. Do not scan every arbitrary string as a URL. URL-only scans also inspect path/query attack indicators, while recording unavailable request-body coverage. Plain payloads have phishing status not_applicable unless an explicit link context exists.

**Core contracts**

POST /api/v1/scans accepts input_type (url/http_request/payload), content, optional content_type, and authorized integration context. Derive project identity from authentication; validate any selected project against memberships. Support structured HTTP input for integration clients to avoid reconstructing lossy raw requests.

Return scan_id, status, risk_score, risk_kind='policy_index', decision, category_scores, findings, coverage, explanation, latency_ms, model_versions, ruleset_version and policy_version. A finding includes detector, category, rule_id where applicable, input_component, normalized-view offsets, redacted excerpt, evidence_kind, and contribution/score with explicit meaning. Missing scores are null, never zero. Preserve original-to-view mappings where available and label offsets clearly.

GET /api/v1/scans lists authorized history with filters and pagination; GET /api/v1/scans/{id} retrieves one result; GET /api/v1/dashboard/summary returns scoped aggregates. POST /api/v1/scans/{id}/review records analyst disposition without automatically retraining. POST /api/v1/enforcement-events accepts authenticated idempotent integration acknowledgements. Provide health/readiness endpoints and a protected policy-management endpoint.

Persistence entities: projects, users/memberships, api_keys (hash only), scans, findings, model_versions, policy_versions, review_events, enforcement_events. Store timing, coverage, versions and redacted summaries; do not store complete request bodies by default. Include retention/deletion behavior and access checks for every history/export route. Escape all attack excerpts in the UI.

**Risk and decision policy v0**

Use five category outputs: phishing, SQLi, XSS, command injection and traversal. Maintain separate ML scores and rule evidence. Initial unified policy index: R = max(r_phishing, r_sqli, r_xss, r_command, r_traversal) across applicable successful detectors. Each category r is the maximum of its enabled mapped ML score and strongest deduplicated rule severity. Initial rule severity mapping: weak=30, medium=60, high=90. These numbers are proposed policy constants, not measured probabilities. An ML score can initially be shown as 100 times its output, labelled uncalibrated; it must not independently authorize automatic blocking before validation. Avoid averaging away a strong attack finding or repeatedly counting one signature across decoded views.

Provisional decision bands: 0–29 Allow; 30–79 Review; 80–100 Block candidate. A candidate becomes Block only when a versioned, tested rule/context is enforcement-eligible or a model has passed its validation/calibration gate. Otherwise Review. Missing required coverage, timeouts, parse ambiguity and unavailable models force Review even with a low observed score; if no useful analysis completed, risk_score is null. Independently verified block-eligible evidence can still produce Block despite another detector failing, with degraded coverage recorded. Thresholds must be tuned on validation data and frozen before final testing.

Decision is distinct from enforcement. Manual scans always have action_taken='none'. In monitor mode, a backend logs proposed decisions and permits requests. For the controlled enforce-mode demo, Allow forwards, Block denies before the handler, and Review denies temporarily with a review_required response rather than silently becoming Allow. The adapter uses a configured timeout and reports scanner_unavailable on failure; the initial protected demo fails closed without labelling the outage an attack. Request-count evidence must prove that denied requests never reached the handler. Dashboard 'blocked requests' counts acknowledged enforcement events, not scanner Block recommendations.

**Explanation design**

Show the input component and exact rule match, the transformations used, the model's estimate, and why policy selected the action. Retain SentinelAI's positive linear n-gram contributions with their limited meaning. For phishing, label observed features as observations; global feature importance is not an explanation of a particular prediction. Add a tested local attribution method later if needed. Template explanations are sufficient for the MVP; no LLM is required for scoring or blocking.

**Development roadmap**

Indicative solo effort: 16–23 focused working days. These are planning estimates, not a promise tied to an unseen hackathon deadline. Stages 3 and 4 may require more time if independent labelled data is unavailable.

| Stage | Effort | Deliverable and completion gate |
|---|---:|---|
| 1. Foundation and contracts | 1–2 days | New repository structure, model manifests, typed scan/finding schema, supported input policy and deterministic fixtures. Existing baselines load behind adapters; no copied legacy UI. |
| 2. Unified detection core | 2–3 days | Parser, normalization views, phishing adapter, request ML adapter and rule engine feed one result. Verify URL/HTTP/payload routing, literal JSON '+', IPv6, shortener boundaries, encoded and multiple-category evidence. |
| 3. Phishing data repair | 3–4 days | Add diverse labelled legitimate URLs, provenance and domain/source splits. Fix feature bugs, retrain, calibrate on held-out validation. Known benign URL regression set must pass; report independent false positives before enabling model blocking. |
| 4. Request data and policy | 3–4 days | Expand benign and attack examples with source/template groups; separate synthetic and independent results. Tune thresholds, preserve uncertainty and verify conflict/missing-detector behavior. Compare ML-only, rule-only and hybrid. |
| 5. API and persistence | 2–3 days | Authenticated scan/history/summary APIs, project scoping, redaction, migrations and version lineage. Restart retains history; unauthorized cross-project reads fail; secrets stay out of exports. |
| 6. Unified interface | 2–3 days | Single composer and result workspace; risk, evidence, decisions, filtered history and operational dashboard from the real API. Exercise empty/error/loading states and safely rendered attack text. |
| 7. Protection integration | 2 days | One demo app adapter and submitted-link workflow use the same API. Demonstrate monitor/enforce behavior, Allow, Review, Block and scanner timeout; verify handler counters and acknowledgements. |
| 8. Release and presentation | 1–2 days | Reproducible environment, final evaluation, deployment readiness, sample requests, architecture and recorded end-to-end demo. Publish only supported performance claims. |

Suggested repository areas: backend/app/{api,schemas,parsing,detectors,risk,explanations,storage,integrations}; frontend/; ml/{datasets,training,evaluation,artifacts}; tests/{unit,integration,regression}; demo-app/; docs/. Pin dependencies after compatibility checks; store model hashes and feature schema versions alongside each artifact. One backend deployment is enough for the MVP; introduce queues or services only when measured load needs them.

**Evaluation and release gates**

Split phishing examples by registered domain and source, and by time when reliable timestamps exist; group attack examples by source/template to keep near-duplicates apart. Split before augmentation. Fit feature transformers only on training data. Reserve validation for model selection, calibration and thresholds; evaluate the frozen system once on the untouched test set. Do not fabricate timestamps where the dataset lacks them.

Report per-category precision, recall, F1, confusion counts and benign false-positive rate, along with dataset sizes and provenance. Also report Review rate, coverage/error rate, blocked-benign rate, and p50/p95 latency on declared hardware and input sizes. Evaluate mixed-category requests separately. Choose the acceptable false-block budget from the demo workload before model promotion; do not announce an arbitrary achieved accuracy target. If independent data is insufficient, release monitor mode with selected tested rules for the controlled demonstration and explicitly label the models experimental.

Regression cases must cover ordinary login/search URLs, quoted code documentation, punctuation and apostrophes, JSON '+', percent/HTML encoding, unsupported multipart/compressed bodies, malformed URLs, duplicate parameters, multiple categories, oversized input, missing model and timeouts. Integration checks must cover actual denial before handler execution, retry-safe event recording, project isolation, safe rendering and redaction. Do not mistake a request containing attack syntax for a demonstrated successful exploit.

**MVP boundary and demo story**

Include all five requested detection categories, ML plus rules, one risk/decision contract, evidence, durable history, a real operational dashboard and one backend integration. Defer browser extensions, arbitrary live URL fetching, HTML crawling, WHOIS/reputation integrations, automatic retraining, broad reverse-proxy support and deep learning until the core is measured. If URL fetching is added later, design a separate restricted fetcher with network destination checks and redirect controls.

The hackathon demonstration: submit an ordinary link and benign request; inspect a suspicious link and a request with multiple attack indicators; see why policy requests Review or Block; send the same cases through the protected demo application; show that the handler was not reached for denied requests; confirm the actual action in shared history. This connects analysis to a real application outcome.

**Reference checks**

The audit findings above come from the supplied files and local probes. The following primary documentation supports implementation choices, not claims about the old projects' performance:

- FastAPI: typed API/OpenAPI features — https://fastapi.tiangolo.com/ and https://fastapi.tiangolo.com/tutorial/
- scikit-learn: prevent data leakage and keep preprocessing inside pipelines — https://scikit-learn.org/1.8/common_pitfalls.html
- OWASP CRS: generic attack rules for compatible WAF engines — https://owasp.org/www-project-modsecurity-core-rule-set/

OWASP CRS is a later baseline or compatible-engine integration option. Its full ruleset is not a drop-in Python regex list, and Prahari's proposed scoring is its own initial policy.
